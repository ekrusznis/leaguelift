# ADR-110 — Phase 31: Athlete Eligibility & Guardian E-Sign Waivers

**Status:** Accepted
**Date:** 2026-08-11

## Context

Phase 31 was fully specified in DESIGN-DOC.md §14.1L (versioned requirement/evidence/clearance model, 10 acceptance criteria) but 100% unbuilt at the domain level as of 2026-08-10 — item 41 of the open-questions list records the 2026-08-06 hybrid-model decision this phase implements: every minor athlete needs current guardian-approved evidence for the applicable sport/program/season before being marked `CLEARED`; provider integrations import waiver acknowledgments/documents only where their approved contracts actually expose them; unsupported, incomplete, expired, or unverifiable evidence falls back to Rally26-native guardian e-sign/upload; roster membership or registration-complete status alone never satisfies a waiver.

The founder asked to begin implementation 2026-08-11, isolated on its own branch — `feature/eligibility_waivers`, one commit per slice, not committed directly to `main` the way mobile persona work has been. All 5 slices below are complete on that branch as of this ADR; the branch is not yet merged.

## Decision

**31.1 — Backend domain foundation** (`7a263f0`). New `com.rally26.eligibility` package and migration `V75`. `eligibility_requirement` rows are versioned and immutable — "editing" inserts a new row sharing `requirement_group_id` at `version + 1` and archives the prior ACTIVE row (a DB unique index enforces exactly one ACTIVE version per group). `eligibility_evidence` is an append-only ledger bound to the exact requirement version signed; a new submission supersedes the prior ACTIVE row rather than overwriting it. `eligibility_clearance` is a recomputed snapshot per (participant, team) that only `EligibilityService.recomputeClearance` ever writes; the absence of a row means `ROSTER_PENDING` (not yet evaluated), deliberately avoiding async infrastructure to give that state real meaning. New capabilities `ORG_ELIGIBILITY_MANAGE` and `TEAM_ELIGIBILITY_VIEW` (granted at every team resource-role tier, including read-only coach access, per §30.2's "coaches see clearance state, never the underlying evidence"). Real endpoints (owner requirement CRUD; coach-facing clearance list with a `status` filter, added mid-slice at the founder's request to support filtering a roster to just `INELIGIBLE` players) shipped with no caller yet — deliberately deferred to whichever slice first gives a guardian something to do about a fresh `DOCUMENTS_REQUIRED` assignment.

**31.2 — Native guardian e-sign/upload, web** (`778a933`). `EligibilityService.listRequirementsForParticipant` (guardian/athlete-self/staff read) and `submitGuardianEvidence` (guardian/athlete-self write — rejects `STAFF_MANUAL_VERIFICATION`/`EXTERNAL_IMPORT`, validates `FILE_UPLOAD` requires a `documentAssetId`, records as `MANUALLY_VERIFIED`, recomputes clearance across every one of the participant's team assignments since one requirement can satisfy more than one team's clearance at once). `MediaEntityAccessService`'s `PARTICIPANT` case was widened to allow the `DOCUMENT` usage slot, reusing the existing guardian-relationship/athlete-self access check rather than a new access-control path. New `frontend/src/features/eligibility/` module with two UI surfaces: an owner-facing requirement builder (new Organization Detail Page tab, modeled on the existing `FeeTemplateList.tsx` CRUD pattern) and a guardian-facing panel added next to the existing "Teams" toggle on each household participant row, with the right action per requirement mode.

**31.3 — Provider eligibility-evidence discovery** (`bebecbd`). Research surfaced a hard constraint that reshaped this slice: TeamSnap and SportsEngine are OAuth *scaffolds* only (Phase 34/ADR-098) — no organization can connect a real account yet, and `SportsDataService`'s direct-import flags are hardcoded `false` for every entity type, not just eligibility. Building a working waiver-import adapter against a live provider API was never possible this slice; there is no live API access to build against. What shipped instead, at the same honest scaffold-level completeness as the rest of that module: `SportsDataEntityType.ELIGIBILITY_EVIDENCE` (migration `V76`) and a `ProviderEligibilityCapabilities` matrix (§30.4/30.5, `IntegrationProvider` → capability set) as real domain data; both scaffold provider clients now emit one stub `ELIGIBILITY_EVIDENCE` record each, proving the existing entity-type-agnostic preview pipeline discovers and reports it with zero changes to `SportsDataService`'s core logic. Still preview-only — no commit path into `EligibilityService.recordEvidence` exists, matching every other sportsdata entity type's current state. GameChanger gets no adapter at all, matching ADR-098 (no public API; roster/schedule only via the existing reviewed CSV import).

**31.4 — Mobile guardian e-sign/upload + coach roster clearance** (`3104ecd`). New `mobile/src/app/eligibility.tsx`, reached from the Parent dashboard's athlete cards (made pressable) and the Athlete persona's More tab. Supports native acknowledgment and e-sign fully. `FILE_UPLOAD` requirements do not get a native upload flow — mobile has no document-picker/media-upload capability of any kind today (confirmed: no such dependency exists, and the existing Documents screen is acknowledge-only) — rather than add a new native dependency requiring another native rebuild cycle immediately before an APK build, `FILE_UPLOAD` shows an explanatory message and, for the Parent flow (which has a `householdId`), a "Continue on rally26.com" button reusing the existing WebView-embed pattern (ADR-106). Athlete-self `FILE_UPLOAD` has no redirect target since athletes have no household page to send them to — just the message. This is a real, acknowledged gap, not glossed over. Separately, `(tabs)/teams.tsx` (Coach's Team Roster) gained a clearance-status badge per player and a "Show ineligible only" filter, using the exact `GET .../teams/{id}/eligibility/clearance?status=` endpoint 31.1 shipped with nothing calling it — also the first real UI for the founder's original mid-31.1 ask. Web still has no equivalent coach-facing roster clearance view; that gap remains open.

**31.5 — Settings/notifications closeout** (`988b4dd`). Correction to earlier planning notes: only `DOCUMENTS_ELIGIBILITY` exists as a real `NotificationTopic` — there is no separate `LEGAL_ELIGIBILITY` category. A bigger finding shaped this slice: the "Documents & eligibility" Settings toggle (shipped Phase 28/ADR-088) was 100% cosmetic — `NotificationDeliveryResolver`, the only code that actually reads a user's notification preference, is wired into exactly two callers (both messaging, topic `MESSAGES`); `AnnouncementService.createSystemAndPublish` — the pipeline behind every existing "Send reminder" button — never consults preferences at all, for any reminder kind, not just eligibility. That inertness predates this phase and is shared by every existing reminder kind; fixing it project-wide was judged a bigger, riskier change than this slice should make as a side effect, since it's shared by campaigns and broadcasts too. What shipped: `AnnouncementKind.ELIGIBILITY_REMINDER` and `ReminderResourceType.ELIGIBILITY` (migration `V77`), a `ReminderService.eligibility(...)` method mirroring the existing `document(...)` reminder exactly — so eligibility reminders now have the same real-world behavior every other reminder kind already has, wired into web's `ParticipantEligibilityPanel` via the existing generic `ReminderButton`. Settings copy that previously said "future eligibility reminders" was corrected since they are real now.

**Verification, every slice:** full backend suite (`./gradlew test`) and `ktlintCheck` green; frontend `npm run typecheck`/`npm run lint`/existing test suite unaffected (5 pre-existing unrelated test failures confirmed present on the branch's own baseline before any Phase 31 change, not introduced by it); mobile `npx tsc --noEmit`/`npm run lint` clean.

## Consequences

- Phase 31's acceptance criteria are met for the Rally26-native path end to end (define → guardian evidence → clearance → coach visibility → reminder) on both web and mobile. The provider-import path (§30.4/30.5) is real, tested infrastructure with no live data behind it yet — activating it is real-OAuth-credential work, not more application code.
- Two real, acknowledged gaps carry forward, not silently closed: no web coach-facing roster clearance view (mobile has one, web doesn't), and no native mobile document-upload capability at all (guardians must finish `FILE_UPLOAD` requirements on web).
- The pre-existing "Settings toggle doesn't gate reminders" issue for every non-MESSAGES topic (campaigns, events, fees, documents, and now eligibility alike) is now a documented, known gap rather than an undiscovered one — worth its own phase if the founder wants every reminder kind to honor per-user preferences, not a Phase 31 fix.
- Branch not yet merged as of this ADR — founder's stated next steps: this DESIGN-DOC/ADR update, then push and merge, then the next mobile APK build.
