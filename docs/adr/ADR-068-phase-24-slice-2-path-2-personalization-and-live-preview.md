# ADR-068: Phase 24 Slice 24.2 — Path 2 Custom Personalization and Live Preview

## Status
Accepted

## Context
Path 1 (ADR-063/065) offered only `LEFT_CHEST`/`RIGHT_CHEST`/`BACK` name/number placement with a fixed logo size, and the buyer order form showed only static, non-overlaid mockup photos. Phase 24 (DESIGN-DOC.md section 14.1G, 24.2) calls for a fourth `CENTER_FRONT` placement, curated small/standard/large logo-size presets, and a live preview — while staying preset-driven, not a freeform design tool.

Printify's real catalog data (confirmed in `ProductService.listVariants`) gives only print-area width/height for each position, never the placeholder's pixel offset within the garment mockup photo. A pixel-exact buyer-facing overlay is therefore not achievable from real data available today.

## Decision
- Added `PersonalizationPlacement.CENTER_FRONT` and a new `SwagLogoSize` enum (`SMALL`/`STANDARD`/`LARGE`) to the domain (`OrderItem.kt`), persisted via migration V49 (`order_item.personalization_logo_size`, plus a widened placement check constraint).
- `SwagDesignCompositor` gained a `personalizationLogoSize` parameter and a private `scaleFactor()` (SMALL 0.72x / STANDARD 1.0x / LARGE 1.3x) applied to each placement's existing fixed logo fraction, clamped to a safe-margin range per placement so a LARGE selection can never overflow the print area. A new `drawCenterFrontLogoAndPersonalization` mirrors the existing chest-placement drawing, centered and sized larger as the "hero" front placement.
- `OrderService.createSwagShopCheckoutSession`/`createInitialFulfillment`, `OrderItemRepository`, `OrderDto`/`OrderController` thread `personalizationLogoSize` straight through, unchanged validation otherwise — `CENTER_FRONT` follows the same front-only path `LEFT_CHEST`/`RIGHT_CHEST` already use, no new `BACK`-style back-print-area requirement.
- Added a buyer-facing `logoPreviewUrl` to `GET .../swag-shop/apparel-types` (`ProductService.getSwagLogoPreviewUrl`, reusing `SwagBrandAssetService.describe()`'s raw-media-asset-id-to-presigned-URL pattern rather than the `MediaAssignment`-based `getPublicDesignUrl`, since a Swag Shop logo is a bare `swagLogoMediaAssetId`, not an assignment). Same no-membership-gate reasoning as the rest of that endpoint — the mockup images it sits alongside are already exposed the same way.
- **Live preview is a deliberate, disclosed approximation, not a pixel-exact rendering.** `SwagPersonalizationPreview.tsx` overlays the logo and typed name/number on top of Printify's real front/back mockup photos using fixed percentage zones that mirror the backend's own fractions/scale factors, with a visible "Preview is approximate — final placement is set at checkout" caption. The backend compositor remains the sole authoritative, exact design generator at checkout confirmation.
- Live-verified end-to-end in a real browser against a manually-fixtured Printify-shaped product/variant: signed in as a real seeded guardian account, confirmed `CENTER_FRONT` and all three logo sizes are selectable, the preview updates immediately on each change, and the front/back split still matches `BACK` placement's dual-canvas behavior.
- **Addendum — real-Printify-account verification found and fixed three further defects, none specific to 24.2's own new code:**
  1. `PrintifyImageClient.uploadImage` sent Printify a fetchable `url` (our storage's signed GET URL) for product-creation's design upload. This fails whenever Printify's servers can't reach that URL — true for local/self-hosted storage, and for any expired signed URL — confirmed live via a real `400 Bad Request: "Failed to upload image"` when creating a fresh Printify product against this environment's real test-account token. Fixed by switching to Printify's `contents` (base64) upload form: the backend already holds the bytes in its own storage (`SpacesClient.getObjectBytesCapped`) and simply forwards them, so no external reachability is required in any environment — a strictly more robust design, not an environment-specific workaround.
  2. `ProductManagementPanel`'s Printify/manual variant price and cost fields required raw minor-unit cents entry (e.g. "2500" for $25.00). Fixed via a schema-level dollars-to-minor-units transform (`schema.ts`), with the edit-variant path converting stored minor-unit values back to dollars for display.
  3. `SwagPersonalizationPreview`'s name/number overlay used dark navy text with a light drop-shadow, illegible against a dark garment — confirmed live against a real navy hoodie mockup where the text was present but essentially invisible. Fixed to white text with a black outline (four offset text-shadows), legible against any garment color, matching real jersey-lettering convention.
  4. Verified against three freshly-created real Printify products (shirt, hooded sweatshirt, sweatpants): shirt and hoodie both got real per-variant cost and real photorealistic mockups, with the live overlay confirmed correct on both by direct pixel inspection. The sweatpants blueprint uses per-leg placeholders (`left_leg_front`/`left_leg_back`) rather than `front`/`back`; its variant has a real cost/price but no captured mockup under the existing (pre-24.2, ADR-065) mockup-capture logic, which only recognizes `front`/`back` camera labels — left as a documented, separate gap for a future slice, not a 24.2 regression.

## Consequences
- A buyer sees a live, responsive preview of their choices for the first time in Swag Shop, without the codebase claiming a precision (pixel-exact placement) it cannot back with real Printify placeholder-offset data.
- The frontend and backend placement math are maintained in two places (`SwagPersonalizationPreview.tsx` and `SwagDesignCompositor.kt`); a future change to one's fractions should update the other's comment cross-reference, though exact numeric parity is not required since the preview is explicitly approximate.
- Path 2's remaining slices (public athlete storefront, Printify shop separation, timezone foundation, registration-wizard foundation, multimedia Help) are unaffected and unblocked by this slice.

## Alternatives Considered
- Fetching Printify's mockup generation metadata for a real placeholder offset: rejected — Printify's catalog API doesn't expose this, and this codebase's own discipline (ADR-035, ADR-062) rejects fabricating a live-integration behavior it can't verify.
- Pixel-perfect canvas-based client preview (rendering the same coordinates as the backend directly onto an offscreen canvas matching print-area dimensions, then compositing over the mockup): rejected as a premature, higher-effort design for a preset-driven feature explicitly scoped as "not an open design tool" — the simpler percentage-overlay approach already gives a buyer an accurate sense of placement/size choice.
