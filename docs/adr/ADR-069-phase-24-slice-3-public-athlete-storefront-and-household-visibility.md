# ADR-069: Phase 24 Slice 24.3 — Public Athlete Storefront and Household Visibility

## Status
Accepted

## Context
DESIGN-DOC.md section 14.1G's 24.3 calls for a public, unauthenticated per-athlete Swag Shop storefront: an org publishes a stable-slug/QR-code page for one specific athlete, a supporter with no Rally26 account can buy an approved product for that athlete, confirmed payment becomes a Phase 23 (ADR family credit) grant to the athlete's household, and guardians see the resulting order and credit on their dashboard. `V46__family_credit_and_markup.sql`'s own header comment explicitly deferred this ("Swag Shop storefront attribution is Phase 25, not built") — this slice fills that gap.

No public participant/athlete endpoint had ever existed in this codebase before. Per DESIGN-DOC.md section 1's youth-data boundary, exposing any athlete identity publicly required an explicit product decision rather than an assumed default. Resolved with the user ahead of implementation: the public label is first name + last initial only (e.g. "Maya J.", computed server-side — the real last name is never serialized), and org owner/coach publish authority is sufficient with no separate guardian consent gate, matching the existing precedent that team rosters/events already publish participant names under the same authority.

## Decision
- **Migration V50**: `athlete_storefront` (slug-unique, `DRAFT`/`PUBLISHED`/`ARCHIVED`, `team_id` optional) and `athlete_storefront_product` (explicit approved-product selection, not "every active store product") tables; `order.attributed_household_id` (nullable, mirrors `contribution.attributed_household_id`); widened `family_credit_grant_source_type_check` with `STOREFRONT_ATTRIBUTION`.
- **Simplified attribution, by design**: unlike campaign contributions (which need a per-household attribution *code* resolved against a link table, since one campaign can be attributed to any of several households), a storefront is scoped to exactly one participant at publish time. Household attribution is therefore a direct `storefront.participantId -> participant.householdId` lookup at checkout time — no attribution-code/link-table indirection.
- **`AthleteStorefrontService`** mirrors `PublicPageService`'s lifecycle exactly (create/publish/unpublish/archive, slug validation, `DuplicateKeyException` -> 409, `getPublic` never distinguishes not-found from not-published). `create` validates: caller has team-scoped manage capability (or org-manager if org-wide), the participant is on the given team's active roster when a team is specified, the store is `ACTIVE`, and every selected product belongs to that store and is `ACTIVE`. `getPublic` computes the public label server-side (`"${firstName} ${lastName.first()}."`) so the real last name is never sent to the browser.
- **Public read/checkout**: `AthleteStorefrontPublicController` (`GET /public/athlete-storefronts/{slug}`) and `AthleteStorefrontOrderPublicController` (`POST/GET .../orders`) mirror `StorePublicController`/`OrderPublicController` exactly, including the 2-second-poll-friendly status endpoint. The product/variant response is deliberately fuller than the generic `PublicProductVariantResponse` — it includes print-area dimensions, mockup URLs, and a signed logo-preview URL — so the 24.2 `SwagPersonalizationPreview` component works unmodified on a fully public page.
- **`OrderService.createAthleteStorefrontCheckoutSession`** resolves the storefront by slug (published only), validates the chosen variant's product is in the storefront's approved set and store-active, resolves `attributedHouseholdId` directly from the participant, and snapshots it onto the order before Stripe is ever called. `confirmFromWebhook` and `refund` each gained a one-line hook: if the order carries an `attributedHouseholdId`, grant (on confirm) or reverse (on refund) a family credit via `FamilyCreditService`.
- **`FamilyCreditService`** refactored `grantForContribution`/`reverseForRefundedContribution` into thin wrappers over new private `createGrant`/`reverseGrant` helpers, so the new `grantForStorefrontOrder`/`reverseForRefundedOrder` wrappers (using `CreditSourceType.STOREFRONT_ATTRIBUTION`) add zero ripple to `ContributionService`.
- **Guardian dashboard**: `ParentDashboardService.getRecentOrders` — previously 100% hardcoded demo data — is now a real query joining household-attributed orders with their fulfillment status and any `family_credit_grant` row. The frontend already had a working `useParentRecentOrders` hook and backend route wired up from an earlier scaffold; only a UI card (`ParentDashboard.tsx`, gated by a new ungated `parent.orders` widget-registry entry, same pattern as the sibling `parent.family-credits`/`parent.outstanding-balance` cards) was missing.
- **Admin UI**: a new `AthleteStorefrontPanel` in the Swag Shop management tab — create (team → roster-scoped athlete picker, store picker, active-product checklist, slug), publish/unpublish/archive, and a copy-link/QR-code control reusing the existing `QrCodeGenerator`/`useBuildAthleteStorefrontShareLink` pattern from sponsorship packages.
- **Public buyer page**: `PublicAthleteStorefrontView.tsx` at `/swag-shop/athlete/:slug` — structurally "the 24.2 buyer flow, minus the athlete-picker and auth, plus the storefront's fixed athlete label," reusing `SwagPersonalizationPreview` and the placement/logo-size UI from `SwagShopOrderFlow.tsx` unmodified.

## Live Verification
Verified end-to-end in a real browser against this environment's real seed data (org `Riverside Youth Sports Club`, athlete `Maya Johnson` on the `Varsity Soccer` roster, real Printify product `Riverside Youth Hoodie` with a real team-logo assignment and a real captured mockup from earlier Printify verification):

1. Created and published a storefront for Maya Johnson via the real admin UI; the QR code and copy-link controls rendered a real `data:image/png` QR encoding `http://localhost:5173/swag-shop/athlete/maya-johnson`.
2. Opened that link in a browser tab with no session. The page showed "Maya J. — Varsity Soccer" / "Riverside Youth Sports Club" (never the real last name), the real Printify front mockup with the real team logo composited on it, and — after selecting `BACK` placement with a name/number — the real live preview text overlay, all reusing 24.2's component unmodified.
3. Completed a real Stripe test-mode checkout (test card, real shipping address) as an unauthenticated supporter ("Grandma Sue"). The resulting `order` row carried `attributed_household_id` equal to the Johnson Family's real household id — confirming the direct participant-to-household attribution path, not a stale or default value.
4. Replayed the checkout's real `checkout.session.completed` Stripe event to the local webhook endpoint (Stripe CLI listener + manual signature construction, since no long-running webhook forwarder was active in this session). The order transitioned to `CONFIRMED` and a real `family_credit_grant` row appeared: `STOREFRONT_ATTRIBUTION`, `AVAILABLE`, $4.00 (the org's configured 10% default credit percent of the $40.00 order) — sourced correctly to the order id, targeted correctly to the Johnson Family household.
5. Fetched the guardian dashboard's real `recent-orders` endpoint for that household and confirmed it returns exactly the shape `ParentDashboard.tsx`'s Recent Orders card renders: product name (`"Riverside Youth Hoodie - Navy / M"`), fulfillment-overridden status, and the granted credit amount/state.
6. A replayed webhook did not create a second grant (idempotency), confirmed both by this live pass and by the corresponding integration test.

**One real, environment-only bug found and fixed during verification, not a code defect**: the first live attempt to create a storefront failed with a generic 500. The backend process that had been running continuously earlier in this session predated migration V50 on disk and had never been restarted to pick it up, so `athlete_storefront` did not yet exist in the shared local database — Flyway only migrates at application startup. Restarting the backend applied V50 immediately and resolved it; this is a local-workflow staleness issue (already a known class of issue this session, see prior auth-rate-limiter restart note), not a defect in the migration, the service, or the schema itself.

**One real, known-class gap surfaced but intentionally not fixed this slice**: the storefront order's Printify draft-order submission failed (fulfillment `FAILED`, no `printify_order_id`) against this environment's real, long-lived fixture Printify product. The order correctly stayed `CONFIRMED` regardless — exactly the documented, tested "Printify unreachable/invalid" fallback behavior `OrderService.confirmFromWebhook` already had before this slice (and asserted by both the pre-existing unit test and this slice's own `createAthleteStorefrontOrderIntegrationTest`, using a `MANUAL` product specifically to keep that scenario deterministic). Diagnosing why one specific long-lived fixture product's real Printify order submission now fails is a Printify-catalog/token maintenance question, not a 24.3 code defect — attribution and credit-grant correctness, this slice's actual scope, were unaffected.

## Consequences
- Rally26 now has its first-ever public, unauthenticated endpoint that serializes any participant-derived data, gated by a server-computed privacy label rather than trusting callers — any future public-facing athlete data surface should follow this same computed-label pattern rather than reuse the raw `Participant` response shape.
- Household order/credit visibility on the guardian dashboard is now real for the one order pathway that can produce it (published athlete storefronts); a regular authenticated Swag Shop order is still never household-attributed, which is intentional per DESIGN-DOC.md section 1 rather than a gap.
- `FamilyCreditService`'s grant/reversal path is now proven generic over two real source types (`CAMPAIGN_ATTRIBUTION`, `STOREFRONT_ATTRIBUTION`), lowering the cost of a third if one is ever needed (e.g. sponsorships).
- Phase 24's remaining slices (Printify shop separation, timezone foundation, registration-wizard foundation, multimedia Help) are unaffected and unblocked by this slice.

## Alternatives Considered
- An attribution-code/link-table scheme mirroring campaign contributions: rejected — unnecessary indirection for an entity that is, by product decision, scoped to exactly one athlete/household at publish time.
- A separate guardian consent gate before a storefront can publish: rejected per explicit product decision — org owner/coach publish authority already covers team rosters/events; adding a second-party consent workflow here would be a new pattern this slice did not need to invent.
- Reusing the generic `PublicProductVariantResponse` and separately fetching mockup/print-area data for the storefront's live preview: rejected as an unnecessary extra round-trip — a purpose-built, wider response for this one buyer-facing surface was simpler and keeps `SwagPersonalizationPreview` unmodified.
