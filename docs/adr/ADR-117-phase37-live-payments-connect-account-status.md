# ADR-117 — Phase 37.8: Live Payments buildable pieces

**Status:** Accepted
**Date:** 2026-08-11

## Context

DESIGN-DOC.md §14.4's "Live Payments Launch" gate lists several still-required items before enabling live Stripe payments. Most need production secrets, a legal/accounting review, or infra access this session doesn't have. A research pass identified four items that sounded like pure code gaps buildable in Stripe test mode today: Connect account-status handling, dispute/chargeback handling, enabling Stripe Tax, and Stripe fee reconciliation. This ADR covers what was actually built and, just as importantly, what was deliberately not — and why.

## Decision

**Built: `account.updated` Connect webhook handling.** Before this, the only way Rally26 learned a connected account's Stripe status changed was `PayoutAccountService.refreshStatus` — a manager manually clicking "refresh status," typically only right after onboarding. Stripe can restrict or disable an already-connected account days or weeks later (a compliance flag, expired verification documents, a dispute pattern) with zero prompt for anyone to go check again. `StripeWebhookController` now routes `account.updated` to a new `PayoutAccountService.syncFromWebhook(stripeAccountId, status)`, which looks up the org by `stripe_account_id` (a new repository method — the existing lookup only went the other direction, by `organizationId`), updates the same `chargesEnabled`/`payoutsEnabled`/`detailsSubmitted` fields the manual refresh already wrote, and additionally captures `account.requirements.disabled_reason` (new `disabled_reason` column, V79) — previously nothing captured *why* an account was restricted, only whether it was. `StripeConnectClient` gained a `statusFrom(account: Account)` pure-mapping function so both the manual-pull and webhook-push paths share one place that reads Stripe's `Account` fields, matching the file's own "no other file interprets Stripe fields directly" seam. An unrecognized `stripeAccountId` (a webhook for an account Rally26 never created) is a clean no-op, matching every other handler's "not ours, ignore" posture in this codebase.

**Deliberately not built: dispute/chargeback handling.** The mechanical webhook-intake and ledger-mirroring (a `charge.dispute.created`/`.closed` case, a `recordDisputeLoss` mirroring `LedgerService.recordRefund`'s existing two-entry reversal shape) is real, buildable code. But *who bears a dispute's loss* — the organization (debited like a refund) or Rally26 absorbing it as a cost of being merchant-of-record (per ADR-005's own note that this "needs to be priced into the platform fee... before Live Payments Launch") — is an explicit, unresolved founder decision, not something readable from the repo. Building the mechanics against a guessed policy risks shipping the wrong behavior with real money attached, which is a materially worse outcome than leaving it visibly unbuilt. §14.4 already lists this open; this pass adds no code, only confirms via research that zero handling exists today (not even a partial version) and names the exact decision blocking it.

**Deliberately not built: Stripe Tax (`automatic_tax`).** The SDK call itself (`SessionCreateParams.AutomaticTax.builder().setEnabled(true)`) is a one-line-per-flow change, fully testable today. But two real gaps sit behind that flag: (1) Stripe Tax needs an origin address and state tax registrations configured in the Stripe Dashboard before it calculates anything beyond $0 — dashboard/business work outside this codebase, exactly what §14.4 already lists as required; (2) per-flow taxability is genuinely undecided — a charitable contribution, a sponsorship purchase, and physical merchandise are three different tax categories, and Stripe Tax needs a `tax_code` per line item to categorize correctly. Flipping the flag with no `tax_code` risks either charging sales tax on a donation that shouldn't be taxed or under-taxing a real sale. §19.3 #4 resolved *that* Rally26 uses Stripe Tax as the mechanism; it did not resolve *which tax code applies to which flow*. Shipping the flag without that categorization is worse than not shipping it.

**Deliberately not built: Stripe fee reconciliation.** Confirmed via research that this genuinely does not exist in any form — the existing `reconciliation` module (`ReconciliationService`/`ReconciliationPanel.tsx`) is a same-named but unrelated feature (internal database self-consistency checks: missing ledger entries, missing provider references — never a comparison against Stripe's own `balance_transaction`). No `LedgerEntryType` member exists for Stripe's own processing fee; the ledger currently assumes the full gross charge amount lands cleanly in Rally26's Stripe balance, net only of Rally26's own platform fee. Building this properly needs a design decision this pass didn't have time to make carefully: whether to fetch `Charge.balanceTransaction.fee` synchronously during payment confirmation (couples payment-confirmation reliability to a third Stripe API call succeeding) or as a separate, later, non-blocking reconciliation step (safer, but a real architectural addition, not a quick call-site change). Rushing this under time pressure risked either coupling a critical path to an extra failure point or shipping a half-considered async design — left for its own dedicated pass rather than guessed at here.

## Consequences

- Connect account-status visibility is real and live-testable today (Stripe CLI/dashboard `account.updated` test events against a test-mode Express account) — closes a real gap where account restrictions could go unnoticed indefinitely.
- Three of §14.4's four researched items remain open, each with a named, specific blocker recorded here (a founder policy decision, a founder tax-categorization decision + dashboard config, and an architecture decision about failure-mode coupling) rather than left as a vague "still required" line.
- Full backend suite green, ktlint clean, two new focused test files covering the webhook-to-service path and the no-op/unknown-account case.
