# ADR-071: Phase 24 Slice 24.5 — Timezone Foundation

## Status
Accepted

## Context
Before this slice, `Event.timezone: String` was already real, persisted, and validated (`EventService.requireValidTimezone` via `ZoneId.of(...)`), and every instant field (`startAt`/`endAt`/`arrivalAt`/`meetingAt`) was already a UTC-safe `Instant?`. ICS export (`IcsCalendarProvider`) already emitted correct UTC `DATE-TIME` values. The real gaps: `EventService.create` required the caller to supply `timezone` with zero smart default anywhere in the system; `Organization` had no address field at all; `Team`/`Tournament` had no timezone concept; no all-day/`DATE`-only event concept existed; no shared `TimeZoneService` existed; and no DST handling existed anywhere.

DESIGN-DOC.md §14.1G's target for 24.5:

> Owner onboarding suggests an IANA timezone from the entered organization address and requires confirmation. Browser timezone is a convenience fallback, never the sole source of truth. Organization default may be overridden by team or tournament settings. Events snapshot the intended timezone; later setting changes do not shift the event's intended wall-clock time. Persist instants in UTC and true all-day dates as `DATE`. A shared service performs input conversion, effective-zone resolution, API/notification/report/ICS conversion, and explicit handling of DST gaps/overlaps.

**Confirmed with the user ahead of implementation** (same category of gap as the Printify token in ADR-070): there is no geocoding integration or credential in this codebase, and none is provisioned by this slice. "Suggest a timezone from address" is satisfied with a static, built-in country/state → canonical IANA timezone heuristic, not a real geocoding API call — DESIGN-DOC only requires a *suggestion* the owner must actively confirm, so an approximate, honestly-labeled heuristic satisfies the acceptance criterion.

**A second scope decision, made mid-implementation at the user's request**: every event-facing date/time display gets a fixed `dd/mm/yyyy HH:mm <zone abbreviation>` line (e.g. "15/08/2026 14:00 EDT"), always rendered in the *event's own* IANA timezone rather than the viewer's, so a value is legible and unambiguous regardless of the reader's locale or timezone. Presented via `AskUserQuestion` were three sub-decisions: format the display client-side (not by adding formatted-string fields to backend DTOs) using the raw `Instant` + `timezone` the API already returns; scope it to `Event` only, since Event is the only entity in this slice with a real, per-record IANA timezone (Order/Fulfillment/audit rows are plain UTC instants with no per-record timezone concept the same way); and use the literal fixed day-first order rather than locale-aware `Intl` formatting, since the whole point of this particular display is a stable, always-the-same-shape value next to its zone, not a locale-adapted one (the existing friendly `Intl.DateTimeFormat(..., {dateStyle, timeStyle})` displays elsewhere in the UI already handle the locale-aware case and were left unchanged).

## Decision

**`organization.timezone` stays nullable, never auto-populated with a default.** A non-null value only ever comes from an explicit owner-initiated confirm action (submitting the profile form with a timezone value) — this makes "the column is set" itself the confirmation signal, with no extra `timezone_confirmed_at` bookkeeping needed. `OnboardingProgress.timezoneConfirmed` is simply `organization.timezone != null`.

**Team/tournament overrides are dedicated update methods, not coalesce fields.** `team.timezone_override`/`tournament.timezone_override` need to be explicitly clearable back to `null` ("inherit"), which a generic coalesce-based update can't express — `TeamRepository.updateTimezoneOverride`/`TournamentRepository.updateTimezoneOverride` set the column directly (never coalesce), matching this codebase's existing convention of a dedicated method wherever a field needs an unambiguous, non-coalesce write (e.g. `archive`, `updateStatus`).

**Resolution order**: team override → tournament override → organization default → hard fallback (`America/New_York`, documented as a real last resort, never presented as authoritative). Team and tournament are already mutually exclusive on an `Event` (existing scope model), so `TimeZoneService.resolveEffectiveZone` never has to arbitrate between both overrides being present.

**DST gap policy = reject.** `TimeZoneService.resolveInstant` computes `zone.rules.getTransition(localDateTime)`; if it's a gap (a local time that doesn't exist, e.g. 2:30 AM on a US spring-forward day), it throws a `ValidationException` naming the exact gap rather than relying on `java.time`'s default silent forward-shift.

**DST overlap policy = earlier offset, deterministic.** An ambiguous local time (e.g. 1:30 AM on a US fall-back day) resolves to `transition.offsetBefore` — the pre-transition offset, which is also the chronologically earlier of the two real instants that local time could mean — computed explicitly rather than relying on `atZone`'s JDK-version-specific default, so the behavior is pinned and unit-tested against real 2026 US DST transition dates.

**All-day events**: new nullable `event.all_day_date date` column; when set, `startAt`/`endAt`/`arrivalAt`/`meetingAt` must all be null — enforced both by a DB check constraint (`event_all_day_excludes_start_at_check`) and application-level validation in `EventService.create`/`update` (the latter also rejects trying to convert an already-timed event to all-day through `update`, since the underlying coalesce-only repository update can't null out the existing instant fields). A `LocalDate` is never converted through any zone, so it can never shift — `IcsCalendarProvider` emits it as an RFC 5545 `DTSTART;VALUE=DATE:yyyyMMdd` / `DTEND;VALUE=DATE:<+1 day>` (exclusive end, per RFC 5545) instead of a `Z`-stamped UTC `DATE-TIME`.

**Event creation keeps its existing snapshot behavior unchanged.** `EventService.create` still takes `timezone: String` as a caller-supplied, permanently-snapshotted value; the new `EventService.resolveDefaultTimezone` (backed by `GET /organizations/{organizationId}/events/timezone-default`) only supplies a smarter *default* to pre-fill the creation form — it never retroactively rewrites any existing event, and a later organization/team/tournament timezone change never touches already-created events (proven directly by a regression test).

**Migration V52** (`timezone_foundation.sql`): adds `organization.address_line1/line2/city/state/postal_code/country` and `organization.timezone` (with a format-check constraint), `team.timezone_override`, `tournament.timezone_override`, and `event.all_day_date` (with the mutual-exclusion check constraint against `start_at`).

**New `timezone/application/` module**: `TimezoneSuggestionService` (the static heuristic — every genuinely multi-zone US state gets its most-populous zone, e.g. FL/TX/TN/MI/KY/ID all default to a single representative zone; a handful of Canadian provinces and single-zone countries; returns `null`, never a guess, for anything unrecognized) and `TimeZoneService` (`requireValid`, `resolveEffectiveZone`, `resolveInstant`, `toLocal` — the single shared source of truth `EventService`, `OrganizationService`, `TeamService`, and `TournamentService` all now depend on).

**Frontend**: `formatEventDateTime`/`formatEventAllDayDate` (`frontend/src/features/events/formatEventDateTime.ts`) are the shared client-side formatters for the fixed `dd/mm/yyyy HH:mm <zone>` display, wired into `EventListPanel`'s event rows and `EventDetailPage`'s header/detail grid. `CreateEventForm`'s timezone field now pre-fills from `GET .../events/timezone-default` (browser `Intl` demoted to the last-resort fallback if that call hasn't resolved yet or the user hasn't touched the field), and gained an "All-day event" checkbox that swaps the four `datetime-local` inputs for a single `date` input bound to `allDayDate`. `OrganizationProfileForm` gained address fields plus a "Suggested timezone: X — Use this" banner that never auto-fills without an explicit click (the confirm act is still the form submit). `TeamList`/`TournamentList` gained a per-row "Timezone" toggle exposing set/clear override controls.

## Known, deliberately deferred gap

`CreateEventForm`'s `toInstant()` (`new Date(value).toISOString()`) converts a `datetime-local` input using the **browser's own local zone**, ignoring whichever `timezone` value is actually selected in the same form — so an admin in Denver creating an event explicitly labeled `America/New_York` still gets a UTC instant computed from Denver's local clock, not New York's. This bug predates this slice (found during research for it, not introduced by it) and is out of scope for a "foundation" slice: fixing it needs a JS timezone-aware date library, and none exists in `frontend/package.json` today. The new backend `TimeZoneService.resolveInstant` is built correctly (DST-aware, zone-explicit) so this frontend gap becomes the only remaining piece once a future slice adds a JS zone library. A comment in `EventListPanel.tsx` points future readers at this ADR.

## Live-verified

Against the real local stack (Postgres + backend + frontend), as the seeded Riverside Youth Sports Club owner:
- Set a US/TX address on the organization; the suggestion endpoint returned `America/Chicago`; clicking "Use this" then "Save profile" persisted `organization.timezone = "America/Chicago"` and flipped the onboarding checklist's "Confirm your organization's timezone" item to complete.
- Set Varsity Soccer's team timezone override to `America/Los_Angeles`; opening "Create event" under that team's schedule pre-filled the Timezone field to `America/Los_Angeles` — proving the resolution chain picks the team override over the organization default end to end, not just in unit tests.
- Created a real all-day event ("Independence Day Tournament," 2026-07-04) via the new checkbox; the event list, detail page header, and detail grid all rendered `04/07/2026 (all day)` with no time; the downloaded `.ics` contained `DTSTART;VALUE=DATE:20260704` / `DTEND;VALUE=DATE:20260705`.
- Downloaded the `.ics` for an existing timed event and confirmed it was unaffected: `DTSTART:20260808T130000Z` / `DTEND:20260808T143000Z`, unchanged UTC `DATE-TIME` shape.

Full backend suite (`gradlew ktlintFormat test ktlintCheck`), including new real-Postgres integration coverage (`TimezoneResolutionIntegrationTest`, proving the team → tournament → organization resolution order end to end) passes. Frontend `tsc -b --noEmit` and `vitest run` pass; the only 7 pre-existing frontend test failures are in files this slice never touched (marketing homepage, a QuickBooks panel bug, a site-header dropdown test) and were failing before this slice started.

## Consequences
- A real, tested, DST-aware timezone resolution chain now exists and is reused by every caller (`EventService`, `OrganizationService`, `TeamService`, `TournamentService`) rather than each reimplementing `ZoneId.of(...)` validation independently.
- All-day events are a first-class, DB-enforced concept rather than a convention layered on top of nullable instants.
- The frontend's fixed-format date/time display gives every event a locale-independent, zone-explicit reading next to any locale-friendly one already shown — closing a real ambiguity for cross-timezone staff/guardians.
- The pre-existing `toInstant()` zone-naive bug remains open, explicitly tracked here rather than silently left undocumented; DESIGN-DOC.md's acceptance criterion 8 ("all-day dates do not shift") is met — the bug is about *timed* event creation input, not all-day dates, and is a known, separately-scoped gap.
- Phase 24's remaining slices (24.6 registration wizard, 24.7 multimedia Help Center) are unaffected and unblocked by this slice.

## Alternatives Considered
- A real geocoding API call for the timezone suggestion: rejected — no credential exists or is being provisioned this slice, mirroring the Printify-token deferral pattern in ADR-070; a heuristic satisfies "suggest, owner confirms."
- Silently allowing `java.time`'s default DST gap/overlap handling (forward-shift a gap, arbitrarily pick an overlap offset): rejected in favor of explicit, tested policies — DESIGN-DOC explicitly calls for "explicit handling of DST gaps/overlaps," and silent shifting is exactly the kind of surprising behavior that requirement exists to prevent.
- Backend-computed, pre-formatted display strings added to `EventResponse` for the fixed `dd/mm/yyyy HH:mm zone` display: rejected per the user's explicit direction — the backend already returns the raw `Instant` + `timezone`, and formatting is a presentation concern that belongs client-side; adding formatted-string fields would duplicate logic and couple the API to one display convention.
- Allowing `EventService.update` to convert an already-timed event to all-day (or vice versa): rejected for this slice — the underlying repository update is coalesce-only (matching every other field), so there is no clean way to null out existing instant fields through it; converting would require a dedicated method this slice does not need.
